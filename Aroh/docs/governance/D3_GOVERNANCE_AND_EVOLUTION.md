AROH D3 DEFINES HOW AROH REMAINS CORRECT AS IT GROWS. IT CONTROLS REQUIREMENTS, ARCHITECTURE, PHASES, CHANGE MANAGEMENT, TESTING, SECURITY, DOCUMENTATION, MONOREPO SYNCHRONIZATION, RELEASES, INCIDENTS, TECHNICAL DEBT, AUDITING, AI AGENTS, AND LONG-TERM SYSTEM EVOLUTION.

AROH MUST NEVER BECOME A SYSTEM WHERE IMPLEMENTATION, DOCUMENTATION, ARCHITECTURE, PRODUCTS, DATA, AND AI CONTEXT DRIFT APART WITHOUT DETECTION.

## MASTER STATE MODEL
INTENDED STATE; DOCUMENTED STATE; IMPLEMENTED STATE; DEPLOYED STATE; OBSERVED STATE.
THESE STATES MUST BE COMPARABLE.
THE OBJECTIVE IS NOT TO PREVENT ALL DIFFERENCES.
THE OBJECTIVE IS TO DETECT, EXPLAIN, APPROVE, AND CONTROL DIFFERENCES.

## SOURCE HIERARCHY
APPROVED REQUIREMENT; APPROVED ARCHITECTURAL DECISION; CURRENT VERIFIED IMPLEMENTATION; CURRENT DOCUMENTATION; DERIVED/GENERATED INFORMATION; ASSUMPTION; FUTURE VISION.

WHEN SOURCES CONFLICT:
DO NOT GUESS.
DO NOT SILENTLY REWRITE.
IDENTIFY THE CONFLICT.
IDENTIFY IMPACT.
RECOMMEND RESOLUTION.
APPLY ONLY AFTER THE AUTHORITY IS CLEAR.

## PHASE GOVERNANCE
PHASE 0 = FOUNDATION.
PHASE 1 = MVP ECOSYSTEM.
PHASE 2 = ADVANCED ECOSYSTEM.
PHASE 3 = FUTURE/DOCUMENTED ONLY.
PHASE PROGRESSION IS SEQUENTIAL.
PHASE 3 MUST NOT BE IMPLEMENTED DURING THE INITIAL PROJECT UNLESS EXPLICITLY PROMOTED.

PHASE EXIT REQUIREMENTS:
IMPLEMENTATION; TESTING; ACCESSIBILITY; SECURITY; PERFORMANCE; DOCUMENTATION; DEPLOYMENT; OBSERVABILITY; ACCEPTANCE CRITERIA; REGRESSION CHECK; KNOWN-RISK REVIEW.
A PHASE IS NOT COMPLETE BECAUSE THE FEATURE LIST IS COMPLETE.

## DEFINITION OF READY
BEFORE IMPLEMENTATION:
REQUIREMENT EXISTS; OWNER EXISTS; SCOPE EXISTS; ACCEPTANCE CRITERIA EXIST; DEPENDENCIES ARE KNOWN; SECURITY IMPACT IS KNOWN; DATA IMPACT IS KNOWN; TEST STRATEGY IS KNOWN; DOCUMENTATION IMPACT IS KNOWN.

## DEFINITION OF DONE
CODE WORKS; TESTS VERIFY IT; ACCESSIBILITY IS VERIFIED; SECURITY IS VERIFIED; PERFORMANCE IS ACCEPTABLE; ERROR STATES EXIST; OBSERVABILITY EXISTS WHERE REQUIRED; DOCUMENTATION IS UPDATED; DEPENDENCIES ARE VERIFIED; DEPLOYMENT BEHAVIOR IS VERIFIED.

## CHANGE MANAGEMENT
DISCOVER → IMPACT → PLAN → IMPLEMENT → VALIDATE → SYNCHRONIZE → DOCUMENT → RELEASE → OBSERVE.

EVERY SUBSTANTIAL CHANGE MUST RECORD:
WHAT; WHY; SCOPE; IMPACT; RISK; DEPENDENCIES; TESTING; DOCUMENTATION; ROLLBACK/RECOVERY WHEN REQUIRED.

## BLAST RADIUS
CLASSIFY CHANGES:
LOCAL; PACKAGE; PRODUCT; SHARED SERVICE; ECOSYSTEM; SECURITY-CRITICAL; DATA-CRITICAL; DEPLOYMENT-CRITICAL.
HIGHER BLAST RADIUS REQUIRES STRONGER VALIDATION.

## ARCHITECTURE DECISION RECORDS
USE ADRs FOR SIGNIFICANT DECISIONS INVOLVING:
SYSTEM BOUNDARIES; DATA OWNERSHIP; TECHNOLOGY; SHARED SERVICES; MONOREPO; API CONTRACTS; DATABASE; AUTHENTICATION; AUTHORIZATION; AI; SECURITY; DEPLOYMENT; MAJOR DESIGN SYSTEM RULES.

ADR FORMAT:
CONTEXT; PROBLEM; OPTIONS; DECISION; RATIONALE; CONSEQUENCES; REJECTED ALTERNATIVES; MIGRATION; STATUS.

## DOCUMENTATION
THE 16-VOLUME/164-SECTION AROH DOCUMENTATION SYSTEM REMAINS THE MASTER DOCUMENTATION STRUCTURE.
DO NOT CREATE A SECOND COMPETING DOCUMENTATION ARCHITECTURE.
EVERY IMPORTANT IMPLEMENTATION CHANGE MUST MAP TO AFFECTED DOCUMENTATION.

DOCUMENT STATUS:
PLANNED; DESIGNED; IN DEVELOPMENT; IMPLEMENTED; TESTED; DEPLOYED; DEPRECATED; REMOVED.
NEVER DOCUMENT AN UNIMPLEMENTED FEATURE AS LIVE.

DOCUMENTATION DRIFT:
IF CODE AND DOCUMENTATION DIFFER: DETECT; CLASSIFY; DETERMINE WHICH IS INTENDED; UPDATE THE CORRECT SOURCE; REVERIFY.

## MONOREPO GOVERNANCE
THE MONOREPO MUST REMAIN CONSISTENT WITH ITS PROJECT GRAPH AND APPROVED ARCHITECTURE.
ENFORCE: DEPENDENCY BOUNDARIES; OWNERSHIP; PROJECT RELATIONSHIPS; SHARED PACKAGE CONTRACTS; BUILD GRAPH; TEST GRAPH; VERSION COMPATIBILITY.
WHEN A CHANGE AFFECTS A SHARED PACKAGE, DETERMINE ALL CONSUMERS BEFORE RELEASE.

## MONOREPO SYNCHRONIZATION
PRODUCT SOURCE → DIFF → IMPACT ANALYSIS → RECONCILIATION → AROH UPDATE → TEST → DOCUMENT → VERIFY.

OWNERSHIP & SOURCE OF TRUTH:
ESTABLISH EXPLICIT OWNERSHIP FOR EVERY ARTIFACT:
- PRODUCT_OWNED: LOCAL BUSINESS LOGIC, LOCAL UI, INTERNAL ASSETS. STAYS PRODUCT-LOCAL.
- AROH_OWNED: PLATFORM HUB, ADAPTATIONS, MONOREPO CONFIGURATION. PRESERVED AGAINST UPSTREAM OVERWRITE.
- SHARED_CONTRACT: EXPORTED TYPES, SCHEMAS, SDK CLIENTS, API CONTRACTS. CONSUMED BY AROH ECOSYSTEM.
- PROTECTED_DOWNSTREAM: EXPLICITLY MARKED IN MANIFEST protectedPaths (e.g. BRIDGE CONFIGS, STORAGE WRAPPERS). IMMUTABLE DOWNSTREAM WINS.
- GENERATED_DERIVATIVE: BUILD ARTIFACTS, TRANSIENT FILES, CACHES. EXCLUDED FROM RECONCILIATION.
- AMBIGUOUS: UNRESOLVED OWNERSHIP. MUST FAIL CLOSED RATHER THAN GUESS.

CONFLICT GOVERNANCE:
DETECT CONFLICTS INVOLVING SOURCE CODE, APIS, SCHEMAS, CONFIGURATION, AND DEPENDENCIES.
NEVER SILENTLY RESOLVE A CONFLICT BY OVERWRITING EITHER SIDE.
CONFLICTS MUST PRODUCE A STRUCTURED REPORT (CATEGORY, IMPACT, REQUIRED RESOLUTION) AND BLOCK MUTATION.

PRODUCTS/ INVIOLABILITY:
PRODUCTS/ DIRECTORY IS STRICTLY PROTECTED.
NO REPOSITORY-WIDE SCRIPT, CODE MOD, CLEANUP, OR SYNCHRONIZATION OPERATION MAY ALTER FILES INSIDE PRODUCTS/.
ANY PROPOSED TARGET PATH RESOLVING INSIDE PRODUCTS/ MUST BE REJECTED IMMEDIATELY.

PROVENANCE & AUDITABILITY:
EVERY SYNCHRONIZATION APPLIED MUST APPEND AN IMMUTABLE AUDIT RECORD CAPTURING:
PLAN ID; TIMESTAMP; ACTOR; ACTIONS APPLIED; PROTECTED ARTIFACTS PRESERVED; CONFLICTS PREVENTED; RESULTING MANIFEST VERSION.

## TEST GOVERNANCE
TESTS MUST REPRESENT REQUIREMENTS AND BEHAVIOR.
TEST LEVELS: UNIT; INTEGRATION; CONTRACT; E2E; UI; ACCESSIBILITY; SECURITY; PERFORMANCE; MIGRATION; RECOVERY.
CRITICAL FLOWS REQUIRE FAILURE TESTS, NOT ONLY HAPPY PATHS.
TEST: RETRY; DUPLICATE REQUEST; TIMEOUT; NETWORK FAILURE; AUTH FAILURE; FORBIDDEN ACCESS; STALE DATA; CONCURRENT UPDATE; PARTIAL FAILURE; SESSION EXPIRY; REFRESH; MOBILE; ACCESSIBILITY.

## REGRESSION GOVERNANCE
WHEN A BUG IS FIXED: FIND ROOT CAUSE; FIX SYSTEMIC CAUSE WHERE POSSIBLE; ADD REGRESSION TEST; SEARCH FOR SAME PATTERN; UPDATE DOCUMENTATION IF NECESSARY.

## SECURITY GOVERNANCE
USE A FORMAL SECURITY VERIFICATION BASELINE.
ALIGN APPLICATION SECURITY VERIFICATION WITH A CURRENT STANDARD SUCH AS OWASP ASVS.
COVER: ARCHITECTURE; THREAT MODEL; AUTHENTICATION; SESSION; ACCESS CONTROL; VALIDATION; CRYPTOGRAPHY; ERROR HANDLING; DATA PROTECTION; COMMUNICATION; DEPENDENCIES; BUSINESS LOGIC; FILES; APIs; CONFIGURATION; LOGGING.
SECURITY MUST BE TESTABLE, NOT MERELY DECLARED.

## AI GOVERNANCE
AI AGENTS MUST FOLLOW THE SAME PROJECT RULES AS HUMAN ENGINEERS.
AI MUST: INSPECT BEFORE MODIFYING; PLAN BEFORE LARGE CHANGES; VERIFY BEFORE CLAIMING; DISTINGUISH FACT FROM ASSUMPTION; PRESERVE APPROVED ARCHITECTURE; RESPECT PHASE BOUNDARIES; RESPECT SECURITY; UPDATE DOCUMENTATION; REPORT UNVERIFIED ITEMS.
AI MUST NEVER: FABRICATE TEST RESULTS; FABRICATE DEPLOYMENTS; FABRICATE TOOL RESULTS; DISABLE SECURITY TO PASS TESTS; DELETE TESTS TO ACHIEVE GREEN STATUS; INVENT BUSINESS RULES; INVENT ECONOMIC RULES; GRANT ITSELF PERMISSIONS; IMPLEMENT FUTURE FEATURES WITHOUT AUTHORIZATION.

AI CHANGE RECORD: AGENT; TASK; FILES; SYSTEMS; DECISIONS; TOOLS; TESTS; RESULTS; UNRESOLVED RISKS.

## QUALITY GATES
EVERY RELEASE MUST PASS THE GATES APPROPRIATE TO ITS RISK.
FUNCTIONAL; TYPE; BUILD; LINT; TEST; SECURITY; ACCESSIBILITY; PERFORMANCE; DATA; API; MONOREPO; DOCUMENTATION; DEPLOYMENT; OBSERVABILITY.
CRITICAL CHANGES REQUIRE STRONGER GATES.

## RELEASE
PRE-RELEASE VALIDATION; DEPLOY; HEALTH CHECK; SMOKE TEST; OBSERVE; CONFIRM; DOCUMENT RELEASE.
A DEPLOYMENT PLATFORM SAYING “SUCCESS” IS NOT ENOUGH.

## OBSERVABILITY GOVERNANCE
USE TRACES; METRICS; LOGS.
MEASURE USER-RELEVANT RELIABILITY, NOT ONLY INFRASTRUCTURE HEALTH.
DEFINE SLIs FOR IMPORTANT SERVICES.
DEFINE SLOs WHEN SERVICE MATURITY JUSTIFIES THEM.
TRACK: AVAILABILITY; LATENCY; ERROR RATE; JOB FAILURE; QUEUE DEPTH; DATA FAILURE; AUTH FAILURE; CRITICAL BUSINESS OPERATION SUCCESS; AI TOOL FAILURE; ECONOMIC OPERATION FAILURE.
AN APPLICATION CAN BE “UP” AND STILL BE BROKEN FROM THE USER'S PERSPECTIVE.

## TECHNICAL DEBT
TRACK REAL DEBT.
CLASSIFY: BLOCKING; HIGH; MEDIUM; LOW; ACCEPTED; PLANNED; DEPRECATED.
DO NOT CALL NORMAL FUTURE WORK “TECHNICAL DEBT.”
DO NOT HIDE REAL RISK UNDER “CLEANUP.”

## DEPENDENCY GOVERNANCE
EVERY DEPENDENCY MUST HAVE PURPOSE.
CHECK: SECURITY; LICENSE; MAINTENANCE; COMPATIBILITY; BUNDLE/RESOURCE IMPACT; ARCHITECTURAL FIT.
UPGRADES MUST BE VALIDATED AGAINST: BUILD; TYPES; TESTS; RUNTIME; DEPLOYMENT; DEPENDENT PACKAGES.

SUPPLY CHAIN: PIN OR CONTROL VERSIONS APPROPRIATELY. VERIFY LOCKFILES. MONITOR VULNERABILITIES. REVIEW NEW DEPENDENCIES. REMOVE UNUSED DEPENDENCIES. DO NOT EXECUTE UNTRUSTED BUILD/INSTALL SCRIPTS WITHOUT UNDERSTANDING THEIR EFFECT.

## PERFORMANCE GOVERNANCE
TRACK REGRESSIONS IN: BUNDLE; RENDER; NETWORK; DATABASE; SERVER; BACKGROUND JOBS; AI; STORAGE.
DO NOT OPTIMIZE WITHOUT MEASUREMENT WHEN PERFORMANCE IS NOT OBVIOUSLY BROKEN.

## AI COST GOVERNANCE
MEASURE AI USAGE WHERE APPROPRIATE.
CONTROL CONTEXT SIZE.
USE APPROPRIATE MODEL CAPABILITY.
CACHE SAFE RESULTS.
AVOID UNNECESSARY TOOL CALLS.
DO NOT REDUCE QUALITY UNLESS THE TRADE-OFF IS INTENTIONAL.

## INCIDENT GOVERNANCE
DETECT; ASSESS; CONTAIN; RECOVER; VERIFY; DOCUMENT; ROOT CAUSE; PREVENT.
FOCUS ON SYSTEM CONDITIONS, NOT BLAME.

## DISASTER RECOVERY
CRITICAL BACKUPS MUST BE RESTORABLE.
RECOVERY PROCEDURES MUST BE TESTED.
DEFINE APPROPRIATE RTO/RPO FOR CRITICAL SYSTEMS AS MATURITY REQUIRES.
DO NOT CLAIM DISASTER RECOVERY EXISTS BECAUSE BACKUPS EXIST.

## DESIGN GOVERNANCE
THE AROH DESIGN SYSTEM IS A SHARED SYSTEM.
NEW GLOBAL TOKENS/COMPONENTS REQUIRE EVALUATION.
PRODUCT-SPECIFIC PATTERNS SHOULD NOT BECOME GLOBAL BY ACCIDENT.
GLOBAL DESIGN CHANGES REQUIRE CROSS-PRODUCT IMPACT REVIEW.

## MOTION GOVERNANCE
RISE; ELEVATE; FLOW; EXPAND; ILLUMINATE REMAIN THE AROH MOTION LANGUAGE.
NEW MOTION MUST BE: PURPOSEFUL; ACCESSIBLE; PERFORMANT; CONSISTENT.

## ECOSYSTEM EXPANSION
A NEW PRODUCT MUST DEFINE:
PURPOSE; BOUNDARY; OWNER; IDENTITY; DATA; API; SECURITY; DESIGN; SHARED SERVICES; DEPLOYMENT; OBSERVABILITY; DOCUMENTATION; MONOREPO RELATIONSHIP.
ADDING A LINK DOES NOT EQUAL PRODUCT INTEGRATION.

## SYSTEM AUDIT
WHEN AUDITING AROH, COMPARE: INTENDED; DOCUMENTED; IMPLEMENTED; DEPLOYED; OBSERVED.
REPORT: MATCH; GAP; CONFLICT; DRIFT; RISK; MISSING; UNTESTED; RECOMMENDED ACTION; PRIORITY.
DO NOT CLAIM COMPLETENESS WITHOUT EVIDENCE.

## CONTINUOUS IMPROVEMENT
AFTER SIGNIFICANT MILESTONES REVIEW: REWORK; FAILURES; UNCLEAR REQUIREMENTS; ARCHITECTURAL DRIFT; PROCESS FRICTION; OVERENGINEERING; MISSING AUTOMATION; REPEATED BUG PATTERNS; DOCUMENTATION GAPS.
ONLY ADD PROCESS WHEN IT CREATES REAL VALUE.

## ULTIMATE GOVERNANCE MODEL
AROH MUST BE: INTENTIONAL; TRACEABLE; VERIFIABLE; SECURE; ACCESSIBLE; PERFORMANT; DOCUMENTED; SYNCHRONIZED; RECOVERABLE; EVOLVABLE.
THE SYSTEM MUST ALWAYS BE ABLE TO ANSWER: WHAT IS IT? WHY DOES IT EXIST? WHO OWNS IT? WHAT DEPENDS ON IT? WHAT STATE IS IT IN? WHAT CHANGED? WHY? WAS IT VERIFIED? WHAT HAPPENS IF IT FAILS? HOW IS IT RECOVERED? WHAT DOCUMENTATION DESCRIBES IT? WHAT FUTURE CONSTRAINTS APPLY?

## FINAL D3 RULE
DO NOT ALLOW AROH TO GROW BY ACCIDENT.
EVERY MEANINGFUL CHANGE MUST HAVE PURPOSE, OWNERSHIP, IMPACT ANALYSIS, VALIDATION, TRACEABILITY, DOCUMENTATION, AND A CONTROLLED PATH INTO THE SYSTEM.
AROH MUST NOT ONLY BE CAPABLE OF BUILDING FEATURES.
AROH MUST BE CAPABLE OF REMAINING CORRECT WHILE FEATURES, PRODUCTS, AI, DATA, SERVICES, DEVELOPERS, AND REQUIREMENTS CONTINUE TO CHANGE.
