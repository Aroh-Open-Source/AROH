AROH D1 DEFINES THE COMPLETE EXPERIENCE AND BEHAVIORAL CONTRACT OF AROH. IT DESCRIBES HOW AROH MUST FEEL, HOW EVERY INTERACTION MUST RESPOND, HOW EVERY UI STATE MUST BE REPRESENTED, HOW THE SYSTEM MUST COMMUNICATE PROGRESS AND FAILURE, HOW USERS MOVE THROUGH THE ECOSYSTEM, HOW AI INTERACTIONS MUST FEEL, HOW ACCESSIBILITY MUST WORK, AND HOW PERFORMANCE MUST BE PERCEIVED. THIS IS MACHINE-OPERATING DATA, NOT MARKETING COPY.

AROH MUST FEEL LIKE ONE COHERENT SYSTEM. DIFFERENT PRODUCTS MAY HAVE DIFFERENT PURPOSES, BUT THE USER SHOULD RECOGNIZE THE SAME UNDERLYING AROH THROUGH NAVIGATION, LANGUAGE, DESIGN TOKENS, MOTION, FEEDBACK, ACCOUNT MODEL, ACCESSIBILITY, ERROR BEHAVIOR, AND INTERACTION PATTERNS.

## PRIMARY EXPERIENCE QUALITIES
FAST; CLEAR; RESPONSIVE; INTENTIONAL; CALM; INTELLIGENT; TRUSTWORTHY; CONSISTENT; ACCESSIBLE; PREDICTABLE; RECOVERABLE; PREMIUM; POWERFUL WITHOUT FEELING COMPLEX.

NEVER OPTIMIZE VISUAL IMPRESSION AT THE COST OF RESPONSE CLARITY, ACCESSIBILITY, PERFORMANCE, SECURITY, OR USER CONTROL.

EVERY INTERACTION MUST HAVE:
- INPUT;
- RECOGNITION;
- PROCESSING STATE IF REQUIRED;
- RESULT;
- STATE UPDATE;
- FEEDBACK;
- RECOVERY PATH IF FAILED.

NO IMPORTANT USER ACTION MAY APPEAR TO DO NOTHING.
NO SYSTEM SUCCESS MAY BE SHOWN BEFORE SUCCESS IS VERIFIED.
NO FAILURE MAY END IN A DEAD END WHEN A SAFE RECOVERY PATH EXISTS.

## INTERACTION STATE MODEL
IDLE; HOVER; FOCUS; PRESSED; ACTIVE; SELECTED; DISABLED; LOADING; PROCESSING; QUEUED; SYNCING; SUCCESS; PARTIAL SUCCESS; WARNING; ERROR; RETRYING; OFFLINE; STALE; UNAUTHORIZED; FORBIDDEN; NOT FOUND; CANCELLED; EXPIRED; DEGRADED.

EVERY INTERACTIVE COMPONENT MUST DEFINE THE STATES RELEVANT TO ITS FUNCTION.
- BUTTONS MUST COMMUNICATE ACTIVATION.
- LINKS MUST COMMUNICATE NAVIGATION.
- FORMS MUST COMMUNICATE VALIDATION AND SUBMISSION.
- TOGGLES MUST COMMUNICATE CURRENT STATE.
- ASYNC ACTIONS MUST COMMUNICATE PROCESSING.
- LONG OPERATIONS MUST COMMUNICATE PROGRESS OR STAGE.
- FAILED ACTIONS MUST COMMUNICATE RECOVERY.
- DO NOT USE A GENERIC SPINNER AS A SUBSTITUTE FOR A STATE MODEL.

## PERCEIVED PERFORMANCE
AROH SHOULD FEEL IMMEDIATE FOR LOCAL INTERACTIONS.
DO NOT BLOCK THE USER FOR WORK THAT CAN SAFELY OCCUR IN THE BACKGROUND.
USE OPTIMISTIC UI ONLY WHEN THE SYSTEM CAN SAFELY RECONCILE FAILURE.
USE VERIFIED SERVER STATE FOR SECURITY-SENSITIVE, ECONOMIC, PERMISSION, OR IRREVERSIBLE OPERATIONS.
STABILIZE LAYOUT DURING LOADING.
RENDER AVAILABLE CONTENT BEFORE NON-CRITICAL CONTENT WHEN POSSIBLE.
PRESERVE USER CONTEXT DURING ASYNC OPERATIONS.

PERFORMANCE MUST BE EVALUATED BOTH OBJECTIVELY AND PERCEPTUALLY:
- TIME TO FIRST USEFUL CONTENT;
- TIME TO FIRST INTERACTION;
- INTERACTION LATENCY;
- NAVIGATION LATENCY;
- DATA RESPONSE LATENCY;
- ERROR RECOVERY TIME;
- BACKGROUND COMPLETION TIME.
DO NOT DEFINE PERFORMANCE ONLY AS “PAGE LOAD.”

## NAVIGATION
NAVIGATION MUST BE PREDICTABLE.
CURRENT LOCATION MUST BE CLEAR.
BACK MUST BE MEANINGFUL.
DEEP LINKS MUST PRESERVE INTENDED CONTEXT.
REFRESH MUST NOT RANDOMLY DESTROY VALID STATE.
QUERY PARAMETERS, FILTERS, SEARCH TERMS, SORTING, PAGINATION, AND VIEW STATE MUST PERSIST WHEN THEIR SEMANTICS REQUIRE IT.
MOBILE NAVIGATION MUST PRESERVE INFORMATION ARCHITECTURE WITHOUT SIMPLY SHRINKING DESKTOP.

## SEARCH
SEARCH MUST DISTINGUISH:
- NO RESULTS;
- FILTERED RESULTS;
- FAILED SEARCH;
- UNAVAILABLE SEARCH;
- LOADING SEARCH.

QUERY STATE MUST BE PRESERVED WHEN APPROPRIATE.
RESULTS MUST PROVIDE ENOUGH CONTEXT TO UNDERSTAND RELEVANCE.
SEARCH FAILURE MUST NOT LOOK LIKE “NO RESULTS.”

## FORMS
LABEL EVERY CONTROL.
SHOW VALIDATION AT THE EARLIEST USEFUL MOMENT.
DO NOT DESTROY USER INPUT BECAUSE OF VALIDATION FAILURE.
ASSOCIATE ERRORS WITH THEIR CONTROLS.
DISTINGUISH CLIENT VALIDATION FROM SERVER VALIDATION.
SHOW SUBMISSION STATE.
PREVENT ACCIDENTAL DOUBLE SUBMISSION.
AFTER SUCCESS, SHOW THE ACTUAL RESULTING STATE.

## ERROR EXPERIENCE
ERRORS ARE NORMAL SYSTEM STATES.
THE USER SHOULD KNOW:
- WHAT HAPPENED;
- WHETHER THEIR DATA WAS PRESERVED;
- WHETHER THE OPERATION MAY HAVE COMPLETED;
- WHETHER RETRY IS SAFE;
- WHAT THEY CAN DO NEXT.

NEVER SAY “SOMETHING WENT WRONG” WHEN MORE USEFUL INFORMATION CAN BE PROVIDED SAFELY.
IF OPERATION STATUS IS UNKNOWN BECAUSE NETWORK FAILURE OCCURRED AFTER A SIDE EFFECT MAY HAVE HAPPENED, DO NOT PRESENT FAILURE AS CERTAIN. PRESENT AN “OUTCOME UNKNOWN / VERIFYING” STATE AND RESOLVE AGAINST AUTHORITATIVE STATE.

## LOADING
- SHORT OPERATIONS → SUBTLE FEEDBACK.
- MEDIUM OPERATIONS → INLINE PROGRESS.
- LONG OPERATIONS → EXPLICIT PROCESSING STATE.
- MULTI-STAGE OPERATIONS → STAGE INFORMATION WHEN USEFUL.
- BACKGROUND OPERATIONS → JOB STATE.
- UNKNOWN DURATION → INDETERMINATE PROGRESS.
- KNOWN DURATION → PROGRESS WHERE RELIABLE.
NEVER SHOW AN UNENDING LOADER WITHOUT A RECOVERY/ESCALATION PATH.

## CANCELLATION
WHEN AN OPERATION CAN SAFELY BE CANCELLED, PROVIDE CANCELLATION.
CANCELLATION MUST HAVE EXPLICIT SEMANTICS.
IF CANCELLATION ONLY STOPS CLIENT WAITING BUT CANNOT STOP SERVER PROCESSING, COMMUNICATE THAT DISTINCTION.
DO NOT PRETEND A CANCELLED REQUEST WAS NEVER EXECUTED IF THE SERVER MAY HAVE PROCESSED IT.

## MOTION
AROH MOTION USES:
- RISE;
- ELEVATE;
- FLOW;
- EXPAND;
- ILLUMINATE.

RISE COMMUNICATES EMERGENCE.
ELEVATE COMMUNICATES HIERARCHY/IMPORTANCE.
FLOW COMMUNICATES CONTINUITY.
EXPAND COMMUNICATES REVEALING/DETAIL.
ILLUMINATE COMMUNICATES ATTENTION/STATE CHANGE.

MOTION MUST: EXPLAIN; CONNECT; CONFIRM; OR GUIDE.
MOTION MUST NOT: BLOCK; CONFUSE; DISTRACT; CREATE ACCESSIBILITY PROBLEMS; CAUSE PERFORMANCE REGRESSIONS.
RESPECT REDUCED MOTION.

## ACCESSIBILITY
AROH MUST TARGET WCAG 2.2 AS THE BASELINE ACCESSIBILITY REFERENCE FOR WEB EXPERIENCES.
DESIGN FOR: PERCEIVABLE; OPERABLE; UNDERSTANDABLE; ROBUST.
KEYBOARD OPERATION MUST BE COMPLETE.
FOCUS MUST REMAIN VISIBLE AND LOGICAL.
FOCUS MUST NOT BECOME OBSCURED.
DYNAMIC CONTENT MUST BE ANNOUNCED WHEN NECESSARY.
COLOR MUST NOT BE THE ONLY STATE SIGNAL.
TOUCH TARGETS MUST BE APPROPRIATE.
AUTHENTICATION FLOWS MUST BE ACCESSIBLE.
DRAGGING MUST NOT BE THE ONLY WAY TO PERFORM AN ACTION.
REDUCED MOTION MUST BE RESPECTED.

## AI EXPERIENCE
AI MUST FEEL LIKE AN INTEGRATED AROH CAPABILITY, NOT AN UNCONTROLLED CHAT WINDOW.
AI MUST CLEARLY DISTINGUISH:
- ANSWER;
- RECOMMENDATION;
- PLAN;
- TOOL CALL;
- EXECUTED ACTION;
- VERIFIED RESULT;
- FAILED ACTION;
- UNCERTAIN RESULT.

AI MUST NEVER CLAIM TO HAVE DONE SOMETHING IT DID NOT ACTUALLY DO.
WHEN AI IS ABOUT TO PERFORM A HIGH-IMPACT ACTION, THE USER MUST HAVE APPROPRIATE AWARENESS AND CONTROL.
AI MUST NOT BYPASS USER PERMISSIONS.
AI MUST NOT EXPOSE CONTEXT THAT THE USER IS NOT AUTHORIZED TO ACCESS.
AI RESPONSES SHOULD PRESERVE CONTEXT.
THE USER SHOULD NOT NEED TO REPEAT INFORMATION THAT IS ALREADY AUTHORITATIVELY AVAILABLE AND RELEVANT.

## DATA DISPLAY
DISTINGUISH: ZERO; EMPTY; NULL; UNKNOWN; NOT LOADED; NOT AUTHORIZED; FAILED; STALE; PENDING.
NEVER REPRESENT UNKNOWN DATA AS ZERO.
NEVER REPRESENT FAILED DATA AS EMPTY.
NEVER REPRESENT UNAUTHORIZED DATA AS NONEXISTENT WHEN THAT WOULD LEAK RESOURCE EXISTENCE.

## AROS
AROS MUST FEEL HIGH-TRUST AND HIGH-PRECISION.
BALANCE MUST BE VERIFIED.
TRANSACTIONS MUST HAVE CLEAR STATUS.
PENDING MUST NOT LOOK COMPLETED.
FAILED MUST NOT LOOK REVERSED.
REVERSED MUST NOT LOOK FAILED.
HISTORY MUST BE TRACEABLE.
DUPLICATE ACTIONS MUST BE PREVENTED.
REFRESHING DURING A TRANSACTION MUST NOT CREATE CONFUSION.

## AUTHENTICATION
LOGIN; SIGNUP; VERIFICATION; PASSWORD RESET; SESSION EXPIRY; LOGOUT; RE-AUTHENTICATION MUST EACH HAVE EXPLICIT STATES.
SESSION EXPIRY MUST PRESERVE SAFE USER WORK WHERE POSSIBLE.
UNAUTHENTICATED AND UNAUTHORIZED STATES MUST NOT BE CONFUSED.

## RESPONSIVE EXPERIENCE
DESKTOP, TABLET, AND MOBILE MUST BE DESIGNED AS VALID STATES OF THE SAME EXPERIENCE.
CONTENT PRIORITY MUST REMAIN CONSISTENT.
NAVIGATION MUST ADAPT.
DIALOGS MUST ADAPT.
FORMS MUST ADAPT.
TABLES MUST HAVE A SMALL-SCREEN STRATEGY.
AI INTERFACES MUST ADAPT.
TOUCH INTERACTION MUST BE FIRST-CLASS.

## EMPTY STATES
EVERY EMPTY STATE MUST IDENTIFY WHY IT IS EMPTY AND, WHEN POSSIBLE, WHAT THE USER CAN DO NEXT.
DISTINGUISH: FIRST USE; NO CONTENT; NO MATCHES; FILTERED; NOT CONFIGURED; NO ACCESS; TEMPORARILY UNAVAILABLE.

## NOTIFICATIONS
NOTIFICATIONS MUST BE RELEVANT.
NOTIFICATIONS MUST HAVE PRIORITY.
NOTIFICATIONS MUST NOT BECOME NOISE.
CRITICAL EVENTS MUST NOT BE BURIED.
USER PREFERENCES MUST BE RESPECTED.

## CROSS-PRODUCT EXPERIENCE
THE USER'S AROH IDENTITY, NAVIGATION EXPECTATIONS, DESIGN LANGUAGE, ACCESSIBILITY, MOTION, STATUS SEMANTICS, AND SYSTEM FEEDBACK MUST REMAIN CONSISTENT ACROSS PRODUCTS.
PRODUCT-SPECIFIC EXPERIENCE MAY DIFFER WHERE PRODUCT PURPOSE REQUIRES IT.

## RECOVERY
AFTER: REFRESH; CRASH; NETWORK LOSS; SESSION EXPIRY; SERVER FAILURE; PARTIAL FAILURE; NAVIGATION AWAY; TAB DUPLICATION; CONCURRENT UPDATE;
AROH MUST RETURN THE USER TO A SAFE, EXPLAINABLE STATE.
DO NOT LOSE USER WORK WITHOUT JUSTIFICATION.
DO NOT INVENT SUCCESS.
DO NOT SILENTLY OVERWRITE NEWER STATE.

## FINAL D1 RULE
EVERYTHING THE USER CAN SEE OR INTERACT WITH MUST HAVE INTENTIONAL BEHAVIOR.
EVERY IMPORTANT ACTION MUST HAVE A RECOGNIZABLE RESPONSE.
EVERY IMPORTANT FAILURE MUST HAVE A RECOVERY MODEL.
EVERY DATA STATE MUST HAVE CORRECT SEMANTICS.
EVERY AI ACTION MUST BE HONEST.
EVERY PRODUCT MUST FEEL LIKE AROH.
EVERY EXPERIENCE MUST REMAIN FAST, ACCESSIBLE, SECURE, AND PREDICTABLE.
