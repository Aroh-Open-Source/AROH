AROH D2 DEFINES THE INTERNAL EXECUTION MODEL OF AROH: REQUEST ROUTING, DOMAIN OWNERSHIP, DATA FLOW, STATE TRANSITIONS, APIs, EVENTS, QUEUES, BACKGROUND JOBS, AI TOOL EXECUTION, PRODUCT COMMUNICATION, MONOREPO DEPENDENCIES, SYNCHRONIZATION, SECURITY BOUNDARIES, CACHING, DATABASE OPERATIONS, FAILURE HANDLING, OBSERVABILITY, AND SYSTEM RECOVERY.

AROH MUST OPERATE AS A COMPOSABLE SYSTEM OF CLEARLY OWNED DOMAINS, NOT AS A MASS OF MUTUALLY DEPENDENT CODE.

## PRIMARY EXECUTION FLOW
INPUT → IDENTITY → AUTHORIZATION → VALIDATION → ROUTING → DOMAIN LOGIC → DATA/EXTERNAL OPERATION → VERIFICATION → STATE UPDATE → EVENT/INVALIDATION → RESPONSE → OBSERVABILITY.

## AI EXECUTION FLOW
INTENT → CONTEXT → PERMISSION → TOOL SELECTION → INPUT VALIDATION → EXECUTION → RESULT VERIFICATION → STATE UPDATE → RESPONSE.

## BACKGROUND FLOW
TRIGGER → JOB → QUEUE → WORKER → EXECUTION → RETRY/FAILURE → COMPLETION → STATE/EVENT → NOTIFICATION IF REQUIRED.

## DOMAIN OWNERSHIP
EVERY IMPORTANT OPERATION MUST HAVE ONE PRIMARY DOMAIN OWNER.
- UI OWNS PRESENTATION.
- APPLICATION LAYERS ORCHESTRATE.
- DOMAIN SERVICES OWN BUSINESS RULES.
- DATA LAYERS OWN PERSISTENCE ACCESS.
- INTEGRATION LAYERS OWN VENDOR-SPECIFIC COMMUNICATION.
- WORKERS OWN LONG-RUNNING EXECUTION.
- OBSERVABILITY OWNS TELEMETRY.

BUSINESS RULES MUST NOT EXIST ONLY IN UI CODE.
AUTHORIZATION MUST NOT EXIST ONLY IN UI CODE.
CRITICAL DATA INTEGRITY MUST NOT DEPEND ON CLIENT BEHAVIOR.

## SOURCE OF TRUTH
EVERY IMPORTANT ENTITY MUST HAVE AN AUTHORITATIVE OWNER.
DERIVED DATA MUST BE REBUILDABLE OR RECONCILABLE WHEN PRACTICAL.
CACHE IS NOT A SOURCE OF TRUTH.
SEARCH INDEX IS NOT A SOURCE OF TRUTH.
ANALYTICS IS NOT A SOURCE OF TRUTH.
CLIENT STATE IS NOT AUTHORITATIVE FOR SERVER-OWNED BUSINESS DATA.

## DATA CONTRACT
INPUT → SCHEMA VALIDATION → NORMALIZATION → DOMAIN VALIDATION → OPERATION → PERSISTENCE → RESPONSE.
CLIENT VALIDATION EXISTS FOR UX.
SERVER VALIDATION EXISTS FOR TRUST.
DOMAIN VALIDATION EXISTS FOR BUSINESS CORRECTNESS.
DATABASE CONSTRAINTS/TRANSACTIONS PROVIDE FINAL INTEGRITY WHERE APPLICABLE.

## API CONTRACTS
EVERY API MUST DEFINE:
INPUT; OUTPUT; ERRORS; AUTHENTICATION; AUTHORIZATION; SIDE EFFECTS; IDEMPOTENCY; VERSION/COMPATIBILITY; RATE/RESOURCE EXPECTATIONS WHERE REQUIRED.
BREAKING API CHANGES MUST BE EXPLICIT.
DO NOT SILENTLY CHANGE CONTRACTS USED BY OTHER PRODUCTS.

## AUTHORIZATION
AUTHENTICATION ANSWERS “WHO?”
AUTHORIZATION ANSWERS “MAY THIS IDENTITY PERFORM THIS ACTION ON THIS RESOURCE UNDER THESE CONDITIONS?”
CHECK AUTHORIZATION AT THE TRUST BOUNDARY.
NEVER ASSUME A HIDDEN BUTTON IS SECURITY.
NEVER TRUST CLIENT-SUPPLIED ROLE/permission INFORMATION.

## DATA ACCESS
RETURN ONLY DATA NECESSARY FOR THE OPERATION.
MINIMIZE CROSS-DOMAIN DATA EXPOSURE.
KEEP INTERNAL DATA MODELS DISTINCT FROM PUBLIC API MODELS WHEN NECESSARY.

## IDEMPOTENCY
ANY RETRYABLE SIDE-EFFECTING OPERATION MUST HAVE A DUPLICATION STRATEGY.
USE IDEMPOTENCY KEYS, UNIQUE CONSTRAINTS, TRANSACTIONAL GUARANTEES, DEDUPLICATION, OR EQUIVALENT CONTROLS AS APPROPRIATE.
CRITICAL EXAMPLES: AROS TRANSACTION; REWARD GRANT; PURCHASE; ACCOUNT CREATION; PERMISSION CHANGE; NOTIFICATION SEND; EXTERNAL WEBHOOK PROCESSING; JOB EXECUTION.

## CONCURRENCY
ASSUME MULTIPLE REQUESTS CAN MODIFY THE SAME STATE.
ASSUME MULTIPLE TABS.
ASSUME RETRIES.
ASSUME DUPLICATED EVENTS.
ASSUME DELAYED EVENTS.
ASSUME AI AND USER ACTIONS CAN COLLIDE.
USE: TRANSACTIONS; ATOMIC OPERATIONS; OPTIMISTIC CONCURRENCY; VERSION CHECKS; LOCKING; UNIQUE CONSTRAINTS; IDEMPOTENCY; CONFLICT RESOLUTION WHEN JUSTIFIED.

## EVENTS
EVENTS REPRESENT MEANINGFUL DOMAIN FACTS.
EVENTS MUST HAVE: TYPE; VERSION; TIMESTAMP; SOURCE; ENTITY/AGGREGATE REFERENCE; RELEVANT PAYLOAD; CORRELATION/TRACE CONTEXT WHEN REQUIRED.
EVENTS MUST NOT CONTAIN SECRETS.
CONSUMERS MUST EXPECT DUPLICATION AND DELAY WHEN DELIVERY GUARANTEES DO NOT PROVIDE EXACTLY-ONCE SEMANTICS.

## EVENT PROCESSING
RECEIVE → VALIDATE → DEDUPLICATE IF REQUIRED → PROCESS → COMMIT → ACKNOWLEDGE.
DO NOT ACKNOWLEDGE AN EVENT BEFORE REQUIRED PROCESSING IS SAFELY COMPLETE.

## BACKGROUND JOBS
EVERY JOB SHOULD HAVE:
ID; TYPE; OWNER; INPUT; STATUS; ATTEMPTS; CREATED; STARTED; COMPLETED/FAILED; RESULT/ERROR; RETRY POLICY.
VALID JOB STATES: QUEUED; RUNNING; RETRYING; COMPLETED; FAILED; CANCELLED; PARTIALLY COMPLETED.
WORKERS MUST BE SAFE TO RESTART.
RETRIES MUST NOT CREATE DUPLICATE SIDE EFFECTS.

## RETRY
RETRY ONLY TRANSIENT FAILURES.
DO NOT RETRY INVALID INPUT.
DO NOT RETRY FORBIDDEN OPERATIONS.
DO NOT BLINDLY RETRY UNKNOWN SIDE EFFECT STATUS.
USE BACKOFF AND JITTER WHEN APPROPRIATE.
SET RETRY LIMITS.

## TIMEOUTS
EVERY EXTERNAL/REMOTE OPERATION MUST HAVE AN APPROPRIATE TIMEOUT.
NO NETWORK CALL SHOULD WAIT FOREVER.
TIMEOUT MUST NOT AUTOMATICALLY MEAN THE REMOTE OPERATION DID NOT OCCUR.

## CIRCUIT BREAKING/FALLBACK
USE ONLY WHEN THE FAILURE MODEL JUSTIFIES IT.
FALLBACKS MUST NOT RETURN FALSE DATA.
DEGRADED MODE MUST REMAIN SAFE.

## CACHE
EVERY CACHE MUST HAVE:
OWNER; KEY; SOURCE; TTL OR INVALIDATION; STALE POLICY; REBUILD PATH.
CACHE INVALIDATION MUST BE PART OF THE DATA DESIGN, NOT AN AFTERTHOUGHT.

## DATABASE
SCHEMA; OWNERSHIP; INDEXES; TRANSACTIONS; CONSTRAINTS; MIGRATIONS; BACKUP; RECOVERY MUST BE DOCUMENTED.
USE TRANSACTIONS WHEN MULTIPLE RELATED CHANGES MUST SUCCEED TOGETHER.
DO NOT USE TRANSACTIONS BLINDLY FOR EVERYTHING.

## MIGRATION
PLAN → MIGRATE → VALIDATE → DEPLOY → VERIFY.
DESTRUCTIVE MIGRATIONS REQUIRE EXTRA SAFETY.
SCHEMA VERSION MUST REMAIN TRACEABLE.

## AROS EXECUTION
AUTHENTICATE → AUTHORIZE → VALIDATE → IDEMPOTENCY CHECK → ATOMIC ECONOMIC OPERATION → PERSIST → VERIFY → EVENT → RESPONSE.
BALANCE MUST NEVER BE A CLIENT-OWNED NUMBER.
ECONOMIC STATE MUST HAVE AN AUTHORITATIVE RECORD.
TRANSACTIONS MUST BE TRACEABLE.
REPLAY MUST NOT DUPLICATE VALUE.

## MEMBERSHIP
MEMBERSHIP STATE MUST RESOLVE INTO EXPLICIT ENTITLEMENTS.
PRODUCTS SHOULD CONSUME ENTITLEMENTS THROUGH A CONSISTENT CONTRACT RATHER THAN REIMPLEMENTING MEMBERSHIP RULES.

## SEARCH
AUTHORITATIVE DATA → INDEX/DERIVED REPRESENTATION → SEARCH.
INDEX FAILURE MUST NOT CORRUPT SOURCE DATA.
INDEXES SHOULD BE REBUILDABLE WHEN PRACTICAL.

## CMS
DRAFT → REVIEW → APPROVED → SCHEDULED/PUBLISHED → UPDATED/ARCHIVED.
CONTENT STATE MUST BE EXPLICIT.
CACHE/INDEX UPDATES MUST FOLLOW CONTENT CHANGES.

## ASSETS
UPLOAD → VALIDATE → STORE → PROCESS → METADATA → ACCESS CONTROL → DELIVERY.
UNTRUSTED FILES MUST BE VALIDATED.
PRIVATE ASSETS MUST REMAIN PRIVATE.

## AI TOOL ARCHITECTURE
EVERY AI TOOL MUST DEFINE:
NAME; PURPOSE; INPUT SCHEMA; OUTPUT SCHEMA; AUTHORIZATION REQUIREMENT; DATA ACCESS; SIDE EFFECTS; IDEMPOTENCY; FAILURE MODES; TIMEOUT; AUDIT/OBSERVABILITY REQUIREMENTS.
AI MUST HAVE NO IMPLICIT UNIVERSAL AUTHORITY.
TOOLS MUST OPERATE UNDER THE USER'S ACTUAL AUTHORIZATION AND THE SYSTEM'S POLICY.

## AI ACTION
PLAN → PERMISSION → VALIDATION → EXECUTE → VERIFY.
AI MUST NEVER INFER SUCCESS FROM TOOL INVOCATION ALONE.

## AI CONTEXT
COLLECT ONLY AUTHORIZED, RELEVANT CONTEXT.
SEPARATE: CURRENT REQUEST; SESSION CONTEXT; USER PREFERENCES; PRODUCT CONTEXT; LONG-TERM MEMORY; SYSTEM STATE.
MEMORY MUST RESPECT DATA BOUNDARIES.

## PRODUCT COMMUNICATION
PRODUCTS MUST COMMUNICATE THROUGH: STABLE APIs; EVENTS; SHARED CONTRACTS; APPROVED SHARED SERVICES.
AVOID DIRECT CROSS-PRODUCT DATABASE COUPLING UNLESS EXPLICITLY JUSTIFIED.

## MONOREPO
THE MONOREPO IS A SYSTEM GRAPH, NOT JUST A DIRECTORY.
PROJECTS MUST HAVE CLEAR RELATIONSHIPS.
DEPENDENCIES MUST BE TRACEABLE.
BOUNDARIES MUST BE ENFORCEABLE.
AFFECTED PROJECTS SHOULD BE DETECTABLE.
BUILD/TEST WORK SHOULD BE SCOPED TO IMPACTED AREAS WHEN SAFE.
SHARED CHANGES MUST BE TESTED AGAINST THEIR CONSUMERS.
THE SPECIFIC MONOREPO TOOL IS NOT FIXED BY THIS PROMPT. USE THE SELECTED TOOLCHAIN'S PROJECT GRAPH, AFFECTED DETECTION, CACHING, AND BOUNDARY CAPABILITIES WHERE AVAILABLE.

## SYNCHRONIZATION
WHEN AN INDEPENDENT PRODUCT CHANGES:
DISCOVER; DIFF; CLASSIFY; MAP OWNERSHIP; DETERMINE AROH IMPACT; RECONCILE; PLAN; VALIDATE; APPLY; AUDIT.
NEVER TREAT FILE COPYING AS SYNCHRONIZATION. RECONCILIATION IS NOT FILE COPYING.

THE SYNCHRONIZATION LIFECYCLE FOLLOWS A STRICT SEQUENCE:
STATUS → INSPECT → DETECT → DIFF → PLAN → DRY-RUN → VALIDATE → APPLY → STATUS.

THREE-WAY STATE DATA MODEL:
1. LAST SYNCHRONIZED BASELINE (B) RECORDED IN PRODUCT MANIFEST.
2. CURRENT INDEPENDENT PRODUCT STATE (P).
3. CURRENT CANONICAL AROH REPRESENTATION (A).

READ-ONLY & DRY-RUN SAFETY MODEL:
- INSPECTION, DETECTION, DIFFING, AND PLANNING ARE STRICTLY READ-ONLY AND GUARANTEE ZERO DISK MUTATIONS.
- DRY-RUN PIPELINE EXECUTES FULL RECONCILIATION WITH ZERO REPOSITORY MUTATIONS.
- MUTATION (APPLY) REQUIRES EXPLICIT AUTHORIZATION (--confirm) AND ABORTS IF NEW CONFLICTS OR STALE BASELINES EXIST.
- REPEATED SYNCHRONIZATION IS DETERMINISTICALLY IDEMPOTENT.

ABSOLUTE PRODUCTS/ BOUNDARY PROTECTION:
- THE PRODUCTS/ DIRECTORY IS AN INDEPENDENT PROJECT BOUNDARY AND IS STRICTLY PROTECTED.
- READ-ONLY INSPECTION OF PRODUCTS/ FOR THREE-WAY DIFFING IS PERMITTED.
- DIRECT MUTATION OF ANY FILE INSIDE PRODUCTS/ IS RIGIDLY BLOCKED AT THE ENGINE LEVEL AND FAILS CLOSED.

CLI/API CONTRACT & DETERMINISTIC EXIT CODES:
0 = SUCCESS / NO CHANGES REQUIRED
1 = SYNCHRONIZATION FAILED
2 = VALIDATION / CONFIGURATION ERROR
3 = UNRESOLVED CONFLICT
4 = STALE BASELINE / STATE CHANGED SINCE PLANNING
5 = PROTECTED BOUNDARY VIOLATION OR UNSAFE TARGET
6 = INVALID / UNKNOWN PRODUCT
7 = SYNCHRONIZATION PLAN UNAVAILABLE OR INVALID

## OBSERVABILITY
IMPORTANT OPERATIONS MUST BE TRACEABLE ACROSS SYSTEM BOUNDARIES.
USE THREE PRIMARY TELEMETRY SIGNALS: TRACES; METRICS; LOGS.
CORRELATE THEM THROUGH TRACE/REQUEST CONTEXT WHERE PRACTICAL.
A DISTRIBUTED REQUEST SHOULD BE ABLE TO SHOW: ENTRY; SERVICES; DATABASE; EXTERNAL CALLS; BACKGROUND HANDOFFS; RESULT; FAILURE POINT.
METRICS SHOULD MEASURE BOTH SYSTEM HEALTH AND USER-RELEVANT RELIABILITY.
LOGS MUST BE STRUCTURED AND REDACTED.

## SECURITY
TREAT: CLIENT INPUT; TOKENS; FILES; WEBHOOKS; EXTERNAL RESPONSES; AI INPUT; AI OUTPUT; USER-SUPPLIED DATA AS UNTRUSTED AT APPROPRIATE TRUST BOUNDARIES.
APPLY: AUTHENTICATION; AUTHORIZATION; VALIDATION; ENCODING; SECRETS MANAGEMENT; SECURE COMMUNICATION; ERROR SAFETY; DEPENDENCY SECURITY; AUDITABILITY.
SECURITY VERIFICATION SHOULD ALIGN WITH A CURRENT APPLICATION SECURITY STANDARD SUCH AS OWASP ASVS.

## FAILURE ISOLATION
OPTIONAL SERVICES SHOULD FAIL WITHOUT DESTROYING CORE PRODUCT FUNCTION.
CRITICAL SERVICES SHOULD HAVE EXPLICIT HEALTH AND FAILURE STATES.
DO NOT HIDE CRITICAL FAILURE BEHIND FALSE FALLBACK DATA.

## DEPLOYMENT
BUILD → TEST → PACKAGE → DEPLOY → HEALTH CHECK → SMOKE TEST → OBSERVE.
POST-DEPLOYMENT VERIFICATION IS REQUIRED FOR IMPORTANT RELEASES.

## CONFIGURATION
DEVELOPMENT; TEST; STAGING; PRODUCTION MUST BE DISTINCT.
SECRETS MUST NOT LIVE IN SOURCE CODE.

## SYSTEM EXECUTION PRIORITY
DATA INTEGRITY > SECURITY > AUTHORIZATION > CORRECTNESS > USER SAFETY > ACCESSIBILITY > RELIABILITY > PERFORMANCE > MAINTAINABILITY > CONVENIENCE.

## FINAL D2 RULE
EVERY IMPORTANT OPERATION MUST HAVE: AN OWNER; A CONTRACT; AN AUTHORITY MODEL; A VALIDATION MODEL; A SOURCE OF TRUTH; A FAILURE MODEL; A RETRY MODEL; A CONCURRENCY MODEL; AN OBSERVABILITY MODEL; A RECOVERY MODEL; A VERIFICATION MODEL.
NOTHING IMPORTANT SHOULD “JUST HAPPEN.”
